# План эксплуатации БД — роль 4 (DBA)

**Проект №2:** Платформа для LLM-ассистентов.  
**СУБД:** PostgreSQL 16+.  
**Основа:** `03-data-model.md`, `01-schema.sql`, `03-analytics.sql`, методичка «Часть 1», стр. 1–2.

## 1. Мини-план эксплуатации (обязательный артефакт)

### Индексы — три решения

1. **Ускорение аналитики по периодам.** Создать B-tree индексы по `llm_requests.started_at` и `request_errors.occurred_at`. Оба поля используются в фильтрах по началу и концу периода в `03-analytics.sql`.
2. **Быстрый доступ к истории и диалогам.** Индекс `(user_id, created_at DESC)` на `conversations` для списка диалогов пользователя; индекс `(assistant_id, conversation_no, request_no)` на `messages` для поиска сообщений конкретного запроса.
3. **Поиск выданных доступов.** Индекс `(user_id, assistant_id)` на `assistant_access`, чтобы быстро находить ассистентов конкретного пользователя. В обратном направлении уже помогает PK `(assistant_id, user_id)`.

SQL: [`sql/06-indexes.sql`](../sql/06-indexes.sql).

### Безопасность — три решения

1. **Разделить полномочия.** `llm_app` — прикладная роль с чтением, вставкой и ограниченным изменением данных; `llm_analyst` — только чтение таблиц для отчётов. Обе роли `NOLOGIN`: реальные учётные записи подключаются отдельно и получают членство в одной из ролей. Владельцем схемы и объектов остаётся отдельная административная учётная запись.
2. **Применить минимальные привилегии через `GRANT`.** Не выдавать приложению `DROP`, `TRUNCATE` и массовые права `UPDATE/DELETE` на исторические таблицы. Аналитику не разрешать запись. Права `PUBLIC` на таблицы и функции приложения отозвать в выделенной учебной БД.
3. **Сохранять авторизацию на уровне приложения.** `assistant_access.access_role` (`viewer`/`editor`) и `users.platform_role` (`member`/`admin`) — бизнес-роли, а не PostgreSQL-роли. Приложение обязано проверять владельца диалога и полномочия пользователя. `GRANT` не обеспечивает изоляцию строк разных пользователей. В текущем коде `publish_assistant_version` использует `SECURITY INVOKER`, поэтому приложению нужен прямой `INSERT` на `assistant_versions`; защита от обхода публикации потребует доработки функции и модели аутентификации (например, защищённый `SECURITY DEFINER` + RLS).

SQL: [`sql/07-security.sql`](../sql/07-security.sql).

## 2. Резервное копирование и восстановление

Для учебного MVP — **ежедневная полная логическая копия** через `pg_dump` в формате custom. Хранить копии минимум 7 дней, не размещать пароли и дампы с пользовательскими текстами в Git; резервное хранилище должно быть защищено и отделено от сервера БД.

Пример команды (в shell, с настроенным безопасным подключением, подставить название БД):

```bash
pg_dump -Fc -d llm_platform -f llm_platform_$(date +%F).dump
```

Восстановление **в отдельную пустую базу**:

```bash
createdb llm_platform_restore
pg_restore --no-owner --no-acl -d llm_platform_restore llm_platform_YYYY-MM-DD.dump
```

Проверять результат: присутствуют 9 таблиц, PK/FK, данные, функция `publish_assistant_version`, триггер, а также корректно выполняются три аналитических запроса. `07-security.sql` повторно применять к восстановленной БД после проверки владельцев и ролей; роли PostgreSQL не входят в дамп отдельной БД. Тестовое восстановление — не реже раза в месяц.

**Предполагаемые цели:** при ежедневной копии потеря данных при аварии может достигать 24 часов (RPO до 24 ч); RTO не гарантирован и определяется тестовым восстановлением. Для меньшего RPO потребуются архивирование WAL/PITR либо более частые резервные копии. `pg_dump` сам по себе не даёт восстановления на произвольный момент времени.

## 3. Оценка объёмов и нагрузки

Рабочая гипотеза для расчёта, **не фактические замеры**: 100 пользователей, 1 000 LLM-запросов в сутки, 3 сообщения на запрос, в среднем 2 КБ полезного содержимого одного сообщения.

| Показатель | Приблизительная оценка |
| --- | ---: |
| Запросов за год | 365 000 строк в `llm_requests` |
| Сообщений за день | 3 000 строк в `messages` |
| Сообщений за год | 1 095 000 строк |
| Тексты сообщений за день (без накладных расходов) | ≈ 6 МБ |
| Тексты сообщений за год (без накладных расходов) | ≈ 2,19 ГБ |

Размеры индексов, TOAST, метаданных JSONB, журналов WAL, строк запросов и резервных копий добавляются отдельно; оценка не равна итоговому размеру БД. При таком объёме партиционирование на старте не требуется. Крупнейший потенциальный источник роста — `messages.content`, далее `message_metadata.metadata`.

### Что контролировать

- `pg_stat_user_tables`: рост таблиц, `seq_scan`, статистика `n_dead_tup`.
- `pg_stat_user_indexes`: фактическое использование индексов (`idx_scan`).
- `pg_database_size(current_database())`, `pg_total_relation_size('public.messages')`: объём.
- `EXPLAIN (ANALYZE, BUFFERS)` для аналитических запросов после загрузки репрезентативных данных; на пяти тестовых строках последовательное сканирование нормально.
- Штатный `autovacuum` оставлять включённым; по мере роста данных перепроверять планы и статистику.

Проверочный SQL: [`sql/08-dba-checks.sql`](../sql/08-dba-checks.sql).

## 4. Проверка структуры и ограничений (страховка DBA)

Проверка исходного `01-schema.sql`:

- Все **9 таблиц имеют PK**, в том числе составные ключи в `assistant_access`, `assistant_versions`, `conversations`, `llm_requests`, `messages`, `message_metadata`, `request_errors`.
- Связность данных поддерживается **FK** и `ON DELETE RESTRICT`, история запросов не исчезает при удалении родителя.
- Присутствуют **UNIQUE** для `users.email`, ограничения **NOT NULL**, **CHECK** для статусов, ролей, номеров, стоимости, токенов, температуры и объекта JSONB.
- `assistant_versions` защищается триггером от `UPDATE` и `DELETE`; журнал запросов сохраняет номер использованной версии.
- Обнаруженная граница: правило «для failed есть хотя бы одна ошибка» и проверка принадлежности диалога пользователю реализуются приложением, а не CHECK/FK. Кроме того, прямой `INSERT` в версии при правах `llm_app` может обойти функцию публикации.

**Статус:** проверено чтением SQL-исходников; проверка исполнения `08-dba-checks.sql` и реального восстановления должна проводиться на экземпляре PostgreSQL.

## 5. Порядок интеграции и проверок

Файлы не изменяют `01-schema.sql` и остальные материалы предыдущих ролей.

```bash
# Из корня репозитория, в выделенной учебной БД:
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/01-schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/02-versioning.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/04-demo.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/05-checks.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/06-indexes.sql
# Этот скрипт требует владельца объектов и права CREATEROLE:
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/07-security.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/08-dba-checks.sql
```

`03-analytics.sql` содержит `PREPARE`; запускать его и вызовы `EXECUTE` в **одной** сессии. Перед оценкой производительности на реалистичном наборе выполнить `ANALYZE`.

На работающей системе `CREATE INDEX` может блокировать записи, поэтому его планируют на окно обслуживания или используют `CREATE INDEX CONCURRENTLY` вне транзакции. Здесь обычный `CREATE INDEX` предназначен для пустой/учебной БД.

**Ограничения демонстрации:** `NOLOGIN`-роли не являются готовыми логинами, пароли в Git не публикуются; права разработчиков/владельца и существующие членства ролей проверяются отдельно; реальная изоляция пользовательских данных требует дополнительных политик безопасности. Изменения прав следует применять только в выделенной базе проекта.
