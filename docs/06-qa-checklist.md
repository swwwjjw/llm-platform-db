# Проверка данных и запросов — роль 5 (QA)

**Проект №2:** Платформа для LLM-ассистентов.  
**СУБД:** PostgreSQL 16+.  
**Основа:** [ER-модель](03-data-model.md), [SQL-реализация](04-sql-implementation.md), [демонстрационные данные](../sql/04-demo.sql), методичка «Часть 1», роль 5.

## Тестовые данные

В `04-demo.sql` есть два ассистента, три пользователя (`owner`, `editor`, `viewer`), версии настроек, диалоги и пять запросов. Набор содержит запрос с четырьмя сообщениями, неудачный запрос, ожидающий запрос с неизвестной стоимостью, исправленную ошибку инструмента и записи ровно на границах ноября 2026 года. Адреса `example.test` и модели `demo/*` условные.

Для негативных сценариев используются эти же строки: изменение или вставка с заведомо неверными значениями должно завершиться указанной ошибкой PostgreSQL. [Проверочный скрипт](../sql/09-qa-checks.sql) выполняется в транзакции и завершает её `ROLLBACK`, поэтому тестовые изменения не остаются в БД. Скрипт рассчитан на отдельную учебную БД после однократной загрузки `01-schema.sql`, `02-versioning.sql` и `04-demo.sql`.

## Чек-лист: 7 проверок

| № | Сценарий и тестовые данные | Ожидаемый результат |
| --- | --- | --- |
| QA-01 | Подставить запросу версии `2` от другого ассистента; добавить сообщение со ссылкой на отсутствующий запрос. | Оба действия отклоняются составными FK (`23503`). Нельзя смешать историю разных ассистентов или создать сообщение без запроса. |
| QA-02 | Изменить email редактора на уже занятый `owner@example.test`; повторить пару `(assistant_id, user_id)` в `assistant_access`. | Оба дубликата отклоняются UNIQUE/PK (`23505`). У пользователя один канонический email, у пары доступа одна роль. |
| QA-03 | Записать `NULL` в обязательные `assistants.name` и `message_metadata.metadata`. | Обе записи отклоняются `NOT NULL` (`23502`). При этом `llm_requests.cost_usd = NULL` допустим и означает неизвестный расход. |
| QA-04 | Передать недопустимый `status`, отрицательную стоимость, JSON-массив вместо объекта. | Все три значения отклоняются `CHECK` (`23514`); стоимость остаётся точным `numeric`, метаданные — объектом JSONB. |
| QA-05 | Попытаться изменить опубликованную версию; вызвать публикацию от имени `viewer`; проверить ссылку старого запроса после версии `2`. | Изменение отклонено триггером (`23514`), публикация — проверкой роли (`42501`), старый запрос всё ещё ссылается на версию `1`. |
| QA-06 | Запустить `cost_by_assistant` и `cost_by_user` за интервал `[2026-11-01, 2026-12-01)` UTC; сравнить с таблицами ниже. | Считаются **запросы**, а не сообщения. Нижняя граница включена, декабрьская запись с `0.9 USD` исключена. Неизвестная стоимость считается отдельно, сумма известных расходов — `0.03500000 USD`. |
| QA-07 | Запустить `top_errors` за тот же интервал; сравнить с таблицей ниже. | Учтены два события: исправленная ошибка инструмента при `succeeded` и ошибка LLM при `failed`. Ошибка ровно на верхней границе не входит. |

`09-qa-checks.sql` автоматически проверяет отказы QA-01–QA-05 и контрольные факты демоданных для QA-06–QA-07. Для проверки **самих подготовленных запросов** из `03-analytics.sql` их результаты нужно сравнить с приведёнными ниже таблицами: SQL-скрипт QA не подменяет эти запросы их копиями.

## Как выполнить

Из корня репозитория в **отдельной пустой учебной БД**:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/01-schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/02-versioning.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/04-demo.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/09-qa-checks.sql
```

Для QA-06 и QA-07 выполнить в **одной сессии** `psql` (при повторном запуске подготовки в этой сессии сначала `DEALLOCATE ALL`):

```sql
\i sql/03-analytics.sql
EXECUTE cost_by_assistant('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
EXECUTE cost_by_user('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
EXECUTE top_errors('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
```

Успешный `09-qa-checks.sql` выдаёт `NOTICE: OK: QA-01...QA-07` и завершается `ROLLBACK`; при неожиданном принятии неверных данных или расхождении фактов скрипт завершится ошибкой. `ON_ERROR_STOP=1` делает эту ошибку видимой в коде завершения `psql`.

## Страховка модели: найденные границы

- FK гарантируют существование диалога и версии **того же ассистента**, но не проверяют, что пользователь диалога имеет доступ к ассистенту. Это правило проверяет приложение.
- Схема допускает `failed` без строки в `request_errors` и запрос без пользовательского сообщения. Приложение должно сохранять связанные записи одной транзакцией. Отдельная процедура или отложенный триггер могли бы перенести эти гарантии в БД.
- `publish_assistant_version` проверяет переданный `p_created_by`, но сам аргумент не подтверждает личность вызывающего. При прямом `INSERT` в `assistant_versions` можно обойти процедуру публикации, если у роли есть право вставки. Это требует контроля прав и аутентификации на уровне приложения/БД.

**Статус:** чек-лист и SQL-сценарии подготовлены по исходникам. Фактический прогон на PostgreSQL и сравнение результатов `03-analytics.sql` следует зафиксировать после запуска учебной БД.
