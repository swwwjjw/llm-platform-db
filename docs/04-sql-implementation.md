## Реализация модели

Составные ключи перенесены без замены на суррогатные идентификаторы: номер диалога уникален в рамках ассистента, номер запроса и сообщения — в рамках диалога, номер ошибки — в рамках запроса. `bigint GENERATED ALWAYS AS IDENTITY` используется только для `users.user_id` и `assistants.assistant_id`.

Ссылка `(assistant_id, version_no)` не позволяет запросу использовать версию другого ассистента. Через `llm_requests` сообщение однозначно связано с настройками, использованными при обработке. Все ссылки используют `ON DELETE RESTRICT`, чтобы удаление родительской записи не уничтожало историю.

Стоимость хранится в `numeric(18,8)` в USD, температура — в `numeric(4,3)`, время — в `timestamptz`. Отрицательные токены и стоимость запрещены. Для стоимости также запрещён специальный `numeric`-маркер `NaN`. Неизвестные токены и стоимость сохраняются как `NULL`, подтверждённое отсутствие расхода — как `0`.

У `pending` отсутствует время окончания. Для `succeeded` и `failed` оно обязательно и не может предшествовать началу. Верхний уровень метаданных проверяется через `jsonb_typeof(metadata) = 'object'`; новые ключи внутри объекта не требуют изменения таблиц.

## Сценарий публикации версии

`publish_assistant_version` проверяет право владельца или редактора, блокирует строку ассистента через `SELECT ... FOR UPDATE`, определяет следующий номер и вставляет новую версию. Блокировка сохраняется до завершения вызывающей транзакции. Все публикации должны проходить через эту функцию; прямой `INSERT` не обеспечивает протокол блокировок.

При стандартном уровне изоляции `READ COMMITTED` второй вызов для того же ассистента ждёт завершения первого и затем вычисляет номер по обновлённой истории. Для более строгих уровней изоляции приложение должно быть готово повторить транзакцию при конфликте. Триггер отклоняет `UPDATE` и `DELETE` любой опубликованной версии, в том числе ещё не использованной запросами. Возврат к старым настройкам выполняется публикацией их копии под новым номером.

Создание ассистента вместе с первой версией:

```sql
BEGIN;

WITH new_assistant AS (
    INSERT INTO public.assistants (owner_id, name)
    VALUES (1, 'Новый помощник')
    RETURNING assistant_id
)
SELECT public.publish_assistant_version(
    assistant_id, 1, 'demo/model-a', 'Отвечай по существу.', 0.5
)
FROM new_assistant;

COMMIT;
```

Пример предполагает существующего пользователя с ID `1`. В приложении ID берётся из аутентифицированной сессии, остальные значения передаются параметрами. Функция работает с правами вызывающего (`SECURITY INVOKER`); её аргумент `p_created_by` сам по себе не подтверждает личность пользователя. Роли БД и ограничения прямой записи относятся к работе DBA.

## Аналитика

Запросы подготовлены через `PREPARE`: параметры — начало и конец периода `timestamptz`. Полуоткрытый интервал `[from, to)` позволяет складывать соседние периоды без повторного учёта границ.

Расходы суммируются по `llm_requests`, без соединения с сообщениями. Четыре сообщения одного запроса не превращают его стоимость в четыре расхода. Пользователь определяется по владельцу диалога, а не по владельцу ассистента. В выборку входят запросы всех статусов, в том числе неудачные и незавершённые.

`known_cost_usd` — сумма известных расходов; `unknown_cost_count` показывает число запросов, стоимость которых пока неизвестна. Если в группе все суммы неизвестны, `SUM` возвращает `NULL`. Строки без запросов за период в отчёт не входят. Общий расход можно получить суммированием строк отчёта по ассистентам; он остаётся частичным при ненулевом числе неизвестных сумм.

Топ ошибок использует время события и группировку по `(source, error_code)`. Исправленная ошибка инструмента учитывается даже при итоговом `succeeded`. Считаются события ошибок, поэтому несколько ошибок одного запроса дают несколько событий.

## Как запустить

Создать отдельную пустую учебную БД. Из корня репозитория выполнить, подставив свою строку подключения:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/01-schema.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/02-versioning.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/04-demo.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f sql/05-checks.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1
```

В открытом соединении `psql`:

```sql
\i sql/03-analytics.sql
EXECUTE cost_by_assistant('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
EXECUTE cost_by_user('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
EXECUTE top_errors('2026-11-01 00:00:00+00', '2026-12-01 00:00:00+00');
```

В DataGrip выполнять файлы по тому же порядку в одной выбранной учебной БД. `PREPARE` и соответствующие `EXECUTE` должны выполняться в одной сессии. Для повторной подготовки запросов в той же сессии сначала выполнить `DEALLOCATE ALL`. DDL и демонстрационные данные предназначены для однократной загрузки в пустую БД; скрипты не удаляют существующие таблицы.

## Результат проверки

Реализация проверена на PostgreSQL 16.16 в отдельном Docker-контейнере:

- DDL, функции, триггер и демонстрационные данные загружаются без ошибок.
- Все 17 проверок `05-checks.sql` проходят; тестовая версия 3 откатывается.
- Результаты трёх отчётов совпадают с приведёнными выше; пустой период даёт пустую выборку.
- В отдельной копии БД два соединения одновременно публиковали настройки одного ассистента. Второе ожидало блокировку, затем были сохранены версии 3 и 4 без дубликатов. Публикация для другого ассистента в это время прошла независимо.

## Граница ответственности SQL-фрагмента

Реализованы все таблицы ER-модели, ограничения отдельных строк, связи и сценарий публикации. В соответствии с моделью следующие правила требуют транзакций приложения или дополнительных процедур:

- создание ассистента и первой версии одной транзакцией;
- проверка доступа к диалогам и права использования ассистента при отправке запроса;
- создание запроса и ровно одного пользовательского сообщения одной транзакцией;
- сохранение минимум одного события ошибки при переводе запроса в `failed`;
- назначение номеров диалогов, запросов, сообщений и ошибок с учётом конкурентных операций.

Для отправки приложение фиксирует выбранную версию до вызова модели и использует её до завершения запроса. Составные FK обеспечивают корректность ссылки, но не выбирают версию за приложение. Политика индексов, GRANT и резервного копирования остаётся задачей роли 4.
